# 专家团铸造局 (Expert Team Foundry)

根据需求铸造可直接使用的 WorkBuddy 专家团，**并持续为它产出的团队把关版本质量**：拆解角色边界、按人配置最优技能、生成合规包体、通过运行校验，最后用八维量化评分裁决版本迭代该不该合入。

## 类型

Team 型（1 主理人 + 5 团员）

|---|---|---|---|

| demand-architect | 甄明界 | 需求架构师 | 需求 → 域划分与角色编制，定边界 |
| skill-strategist | 施用长 | 技能选型师 | 三源枚举候选技能 → 过滤可用性 → 五维打分选定 |

## 功能

**输入**：一个需求（越具体越好），或一个"这个团该不该迭代"的疑问。
**输出**：`~/.workbuddy/plugins/marketplaces/my-experts/plugins/<name>` 下**真实可用**的专家包 + 四份证据文档（编制表 / 技能选型表 / 质检报告 / 能力基线卡或迭代裁决报告）+ 能力缺口清单。

工作流水线（严格串行）：

```
Phase 1  主理人          接需求 →《需求定义卡》
Phase 2  需求架构师        →《角色编制表》（域划分 + 边界判据 + 不需要的角色）
Phase 3  技能选型师        →《技能选型表》（三源候选 + 可用性过滤 + 量化打分 + 放弃理由）
Phase 4  专家包工程师      → 真实包体（init → 填 → 头像 → validate → register）
Phase 5  质检合规官        →《质检报告》（check_expert_skills --strict 必须退出码 0）
Phase 6  主理人           → 交付 + 能力缺口清单
Phase 7  版本迭代官        →《能力基线卡》（首版）或《迭代裁决报告》（迭代版）
Phase 8  主理人           →《运行基线卡》（实战验收：L1 交付质量 + L2 过程效率）
```

## 它凭什么比"随手生成一个团队"更强

1. **角色边界有判据**：「域内合并、跨域才拆人」；并强制回答"有没有用户会直接问它的问题？"
2. **技能选择有工具**：三源枚举（本地索引 / WorkBuddy 市场 / skills.sh 生态）+ 可用性一票否决 + 五维量化打分；无显著优势时**停下交用户裁决**，不擅自绑定
3. **绑定有门禁**：`check_expert_skills.py` 模拟运行时的技能解析规则，抓出「解析不到」和「能解析但跑不起来」两类静默失败
4. **交付有证据**：编制表、选型表、质检报告必须留档，且命令输出必须真实粘贴
5. **迭代有裁判**：八维能力量化评分 + 显著性阈值 + 回归护栏 + 因果链校验，**把"感觉变强了"变成可证伪的裁决**，并强制拒绝无实质提升的迭代

## 迭代评分卡（八维）

| 维度 | 满分 | 测什么 | 适用 |
|---|---|---|---|
| 技能适配度 | 25 | 有没有为每个角色选到本机最优技能（标准探针口径，同角色跨版本可比） | 全部 |
| 角色边界清晰度 | 15 | 是否声明做什么/不做什么/输入输出契约 | 全部 |
| SOP 完备度 | 15 | 阶段产出物、验收点、反馈回路、串并行决策 | 全部 |
| 健壮性 | 15 | 失败处理、降级替代、停止条件、不确定性声明、前置依赖等待 | 全部 |
| 合规覆盖 | 10 | 用途/来源声明、隐私脱敏、许可风险处置、终审关卡 | 全部 |
| 可验证性 | 10 | 实跑门禁与规范校验、验收条款、产出物可对照 | 全部 |
| 可复现性 | 10 | 选型留痕、淘汰理由、能力缺口清单、工具引用 | 全部 |
| **迭代治理度（D8）** | 10 | 有没有专职治理角色 + 裁决技能 + 裁决规程（阈值/多档/停线）+ 留痕与自指约束 | **仅元团** |

**分母是可变的**：普通业务团（未绑定 expert-manager / expert-skill-selector / team-capability-eval）D8 记为 N/A、不进分母，总分仍为 100 分制；**元团**（产出物是专家包）分母为 **110**。跨版本比较一律按**百分制**（`total_pct`）——直接比绝对分是错的。

**两版维度集合不一致时判 `INCOMPARABLE`**（退出码 35）：标尺变了，总分变化里混了「标尺变化」，不允许据此宣称提升，必须用同一张卡把两版都重测。

**成本项（文件数 / 体积 / 成员数 / 技能数）永远单列，绝不混入能力分**——防止用"写得更长"冒充"能力更强"。

## 迭代七条红线

1. 无预测的改动不受理（必须先写"预期影响哪个维度"）
2. 总分提升 < 6 分或 < 5% → 拒绝迭代
3. 任一维度相对满分倒退 ≥ 10% → 必须交用户裁决，不得自动合并
4. 未过门禁的包不得参与「能力提升」主张
5. 不得用规模冒充能力
6. 不得拿旧标尺量新东西，也不得为单次改动量身定做新维度（加维度必须能回溯检验出区分度）
7. 标尺一改、全部重测；两版维度集合不一致 → `INCOMPARABLE`，任何"提升"主张都不成立

## 使用示例

- 帮我根据这个需求创建一个专家团：（描述你的需求）
- 给我这个专家团的每个角色挑最合适的技能，并确认在本机真的能用
- 对比这个专家团的两个版本，判断这次迭代到底有没有变强、有没有哪一维退步

## 依赖的技能

| 技能 | 被谁用 | 来源 |
|---|---|---|
| `expert-skill-selector` | 技能选型师、质检合规官 | 用户级技能 |
| `expert-manager` | 专家包工程师、质检合规官 | WorkBuddy 内置 |
| `team-capability-eval` | 版本迭代官 | 用户级技能 |

> 本团队**不自带**技能库，因此 `plugin.json` 中不声明 `skills` 字段。

## 头像

头像位于 `avatars/`，512×512 px，单张 ≤500KB。新增成员（版本迭代官）**未配置头像**，`plugin.json` 中不写 `avatar` 字段——头像非必填，缺失不构成规范告警。
