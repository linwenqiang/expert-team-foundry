# 专家团铸造局 (Expert Team Foundry)

这是一个 WorkBuddy 专家包（装上就能用的 AI 小队）。装好之后，你就有了一支六人团队，专门帮你**铸造新的专家团**：你说清需求，它负责拆角色、配技能、把团队真正造出来装进你的 WorkBuddy。

**它能帮你解决什么问题？** 想搭一个 AI 专家团队，通常要自己琢磨角色怎么分、技能怎么挑、配置怎么写，做完了也没人帮你把关。这个团把这些全包了：怎么拆角色有硬判据，技能好不好用要实测，交付前有质检，以后想升级还有专门的「裁判」打分裁决——一切看证据，不凭感觉。

**最快怎么用上？** 打开 WorkBuddy，选中「专家团铸造局」，说一句：

> 帮我根据这个需求创建一个专家团：（在这里描述你的需求）

## 类型

Team 型（1 主理人 + 5 团员）

## 团队成员

| 成员 ID | 名字 | 职业 | 职责（白话版） |
|---|---|---|---|
| expert-team-foundry-team-lead | 秦铸范 | 专家铸造总监 | 队长。接你的需求，指挥全队按步骤干活，最后把成果汇总交给你 |
| demand-architect | 甄明界 | 需求架构师 | 把需求拆成角色分工：团队要几个人、各管什么、边界在哪，还给团起名字 |
| skill-strategist | 施用长 | 技能选型师 | 给每个角色挑技能：多方找候选、逐个实测能不能用、量化打分再定 |
| package-engineer | 包成品 | 专家包工程师 | 把设计图变成真实可用的专家包，并注册到你的 WorkBuddy |
| qa-compliance | 郝验真 | 质检合规官 | 交付前全面体检：查技能绑定、查规范、查隐私合规，问题严重可一票否决 |
| version-iteration-officer | 岳进明 | 版本迭代官 | 裁判。给团队打分，判断一次升级到底该不该通过 |

## 功能

**你给它**：一个需求（越具体越好），或者一个「这个团该不该升级」的疑问。

**它给你**：一个装好就能用的专家包（放在 `~/.workbuddy/plugins/marketplaces/my-experts/plugins/<团名>` 下），外加四份证据文档（角色编制表 / 技能选型表 / 质检报告 / 能力基线卡或迭代裁决报告），和一份「下次还能更好」的能力缺口清单。

工作流水线（SOP，即标准操作流程）共 8 步，严格按顺序走，一步不过关不进下一步：

```
Phase 1  主理人          听你说清需求，整理成一张《需求定义卡》
Phase 2  需求架构师      决定团队要有哪几个角色、各管什么、为什么需要
Phase 3  技能选型师      给每个角色挑最合适的技能，并确认本机真的能用
Phase 4  专家包工程师    把团队生成真正的包体，注册到你的 WorkBuddy
Phase 5  质检合规官      交付前全面体检，问题严重可一票否决
Phase 6  主理人          正式交付，并附上「还差什么」的能力缺口清单
Phase 7  版本迭代官      给团队打分：首版建基线，升级版出裁决
Phase 8  主理人          实战验收，记录真实使用中的效果与效率
```

## 它怎么保证质量

1. **拆角色有硬判据**：能合并就合并，不为了凑数硬拆人；每个角色都要能回答「用户会直接问它什么」
2. **挑技能不拍脑袋**：从多个来源找候选、逐个实测可用性、量化打分；没有明显赢家时**停下来交给你裁决**，不擅自绑定
3. **上岗前有体检**：自动检查技能绑定，抓出「静默失败」（表面跑通了、实际没生效）这类坑
4. **交付留证据**：编制表、选型表、质检报告全部留档，命令输出必须真实粘贴，不接受口头声称
5. **升级有裁判**：用打分表量化比较新旧版本（详见文末附录），有退步就拦下，不许「感觉变强了」就通过

## 使用示例

- 帮我根据这个需求创建一个专家团：（描述你的需求）
- 给我这个专家团的每个角色挑最合适的技能，并确认在本机真的能用
- 对比这个专家团的两个版本，判断这次迭代到底有没有变强、有没有哪一维退步

## 单人直调

不想走全流程？也可以按问题直接找对应成员：

| 你想问什么 | 直接找谁 |
|---|---|
| 这需求该怎么拆角色？ | `demand-architect` |
| 这个角色该挂什么技能？ | `skill-strategist` |
| 帮我把它生成出来 | `package-engineer` |
| 检查一下有没有问题 | `qa-compliance` |
| 这个新版比旧版强在哪 / 该不该合入？ | `version-iteration-officer` |
| 帮我做一个专家团 | 走完整 SOP（找主理人） |

## 依赖的技能

| 技能 | 被谁用 | 来源 |
|---|---|---|
| `expert-skill-selector` | 技能选型师、质检合规官 | 用户级技能 |
| `expert-manager` | 专家包工程师、质检合规官 | WorkBuddy 内置 |
| `team-capability-eval` | 版本迭代官 | 用户级技能 |

> 本团队**不自带**技能库，因此 `plugin.json` 中不声明 `skills` 字段。

## 头像

头像位于 `avatars/`，512×512 px，单张 ≤500KB。版本迭代官（岳进明）暂未配置头像，`plugin.json` 中不写 `avatar` 字段——头像非必填，缺失不构成规范告警。

## 安装与卸载

本专家包位于：

```
~/.workbuddy/plugins/marketplaces/my-experts/plugins/expert-team-foundry/
```

已注册到 `marketplace.json`，在「专家中心 → 我的专家」可见。

```bash
python <expert-manager>/scripts/package_expert.py expert-team-foundry
```

## 附录 A · 迭代评分卡（八维）

版本迭代官用这张卡给团队打分。每个维度有满分上限，测的内容各不相同：

| 维度 | 满分 | 测什么 | 适用 |
|---|---|---|---|
| 技能适配度 | 25 | 有没有为每个角色选到本机最优技能（标准探针口径，同角色跨版本可比） | 全部 |
| 角色边界清晰度 | 15 | 是否声明做什么/不做什么/输入输出契约 | 全部 |
| SOP 完备度 | 15 | 阶段产出物、验收点、反馈回路、串并行决策 | 全部 |
| 健壮性 | 15 | 失败处理、降级替代、停止条件、不确定性声明、前置依赖等待 | 全部 |
| 合规覆盖 | 10 | 用途/来源声明、隐私脱敏、许可风险处置、终审关卡 | 全部 |
| 可验证性 | 10 | 实跑门禁与规范校验、验收条款、产出物可对照 | 全部 |
| 可复现性 | 10 | 选型留痕、淘汰理由、能力缺口清单、工具引用 | 全部 |
| **迭代治理度（D8）** | 10 | 有没有专职治理角色 + 裁决技能 + 裁决规程（阈值/多档/停线）+ 留痕与自指约束 | **仅元团** |

三条配套规则：

1. **分母是可变的**：普通业务团（未绑定 expert-manager / expert-skill-selector / team-capability-eval）D8 记为 N/A、不进分母，总分仍为 100 分制；**元团**（即产出物是专家团的团）分母为 **110**。跨版本比较一律按**百分制**（`total_pct`）——直接比绝对分是错的。
2. **两版维度集合不一致时判 `INCOMPARABLE`**（退出码 35）：标尺变了，总分变化里混了「标尺变化」，不允许据此宣称提升，必须用同一张卡把两版都重测。
3. **成本项（文件数 / 体积 / 成员数 / 技能数）永远单列，绝不混入能力分**——防止用「写得更长」冒充「能力更强」。

## 附录 B · 迭代七条红线

以下任何一条被触发，迭代就不能顺利通过：

1. 无预测的改动不受理（必须先写「预期影响哪个维度」）
2. 总分提升 < 6 分或 < 5% → 拒绝迭代
3. 任一维度相对满分倒退 ≥ 10% → 必须交用户裁决，不得自动合并
4. 未过门禁的包不得参与「能力提升」主张
5. 不得用规模冒充能力
6. 不得拿旧标尺量新东西，也不得为单次改动量身定做新维度（加维度必须能回溯检验出区分度）
7. 标尺一改、全部重测；两版维度集合不一致 → `INCOMPARABLE`，任何「提升」主张都不成立
